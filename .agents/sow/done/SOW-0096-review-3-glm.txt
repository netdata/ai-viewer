## PART A — CANONICAL MODEL COMPLETENESS

### ID: T2-canonical-1
**Invariant**: #2 (USER PROMPTS)
**Severity**: P1 (the invariant as written is structurally inexpressible — it cannot fail because it cannot run)
**Description**: The canonical `OpKind` enum defines exactly seven kinds — `llm`, `tool`, `session`, `reasoning`, `internal`, `system`, `compaction`. There is **no `user_input` kind**. Invariant #2's test (`count(ops WHERE kind='user_input')`) returns 0 for every adapter regardless of whether user prompts are actually captured, because nothing in the canonical contract defines or emits that kind. The invariant therefore cannot distinguish "adapter captured the prompt" from "adapter didn't" — it always reports "didn't".
**Evidence**:
- `internal/canonical/events.go:77-92` — the full `OpKind` const block; `user_input` is absent.
- `internal/store/schema_contract_test.go:364` — `ops.kind` is `TEXT NOT NULL` (free-text), so the column *could* hold the value, but the canonical Go type that adapters construct events from has no constant for it.
- `internal/adapters/codex/ops_response.go:160-161` — codex emits user prompts as `Kind: canonical.OpInternal, Name: "user_input"`, i.e. an overloaded `internal` op, **not** `kind='user_input'`. This is the source of the CTO's "24,149 internal ops (likely user_input misclassified)" observation — they are *not* misclassified, they are the only representation of user input in the model, and they hide behind the `internal` kind that the UI hides by default (events.go:86-87).
**Proposed invariant**: Either (a) rewrite #2 as `count(ops WHERE kind='internal' AND name='user_input')` and accept that it only works for codex, or (b) add `OpUserInput OpKind = "user_input"` to the canonical enum and migrate codex + add the others. The current framing does neither.
**Suggested fix**: Make a **design decision** (operator-facing) and record it in `canonical-events.md`: *Is the user prompt a first-class op, or is it implicitly the turn boundary + the `llm_request` payload body?* Today the codebase does both inconsistently. Do not write the invariant until this is decided.
**Open questions**: Does the operator need to *query* user prompts directly (e.g. "show me all sessions where I asked about X"), or is full-text search over `llm_request` bodies sufficient? If FTS-over-prompts is enough, `user_input` does not need to be an op kind.

### ID: T2-canonical-2
**Invariant**: #2 (USER PROMPTS)
**Severity**: P2 (cross-adapter inconsistency / design smell)
**Description**: Even setting the enum aside, the canonical model has **no documented contract for where a user prompt lives**. Each adapter invented its own representation:
- codex: `internal` op named `user_input` + a body PayloadRef (`codex/ops_response.go:119-169`).
- opencode: user message "must emit nothing" — it is purely a turn-boundary marker; the text is dropped (`opencode/mapper_test.go:376-394`, `opencode/mapper_emitters.go:20-28`).
- claude-code: `ops_user.go` starts a turn but emits **no op** for user text; the user content lives only inside the `llm_request` PayloadRef body.
A 6th adapter written tomorrow would have no canonical guidance on how to represent the user prompt. This is exactly the "completeness contract" gap the SOW's spec-delta #3 wants to close.
**Evidence**: `internal/adapters/opencode/mapper_test.go:380` ("the assistant message IS the turn. The user message must emit nothing"); `internal/adapters/codex/ops_response.go:160`; `internal/adapters/claude_code/ops_user.go:17-25` (only `startUserTurn`, no op).
**Proposed invariant**: A spec-level invariant: "the per-adapter matrix MUST state, for each adapter, one of: (a) emits a `user_input` op, (b) user text is in `llm_request` payload only, (c) not captured — known gap."
**Suggested fix**: Land the per-adapter matrix in `canonical-events.md` before writing invariant code.

### ID: T4-canonical-1
**Invariant**: #4 (ASSISTANT OUTPUT)
**Severity**: P1 (same structural inexpressibility as T2-canonical-1)
**Description**: There is **no `assistant` OpKind**. Invariant #4's primary clause (`count(ops WHERE kind='assistant')`) is dead. The fallback clause `(kind='llm' AND has-response)` *is* expressible, so #4 can be salvaged by deleting the `kind='assistant'` branch — but only if that deletion is a documented decision, not an accident.
**Evidence**: `internal/canonical/events.go:77-92` (no `assistant`); `internal/adapters/codex/ops_response.go:79` (assistant message → `Kind: canonical.OpLLM`); `internal/adapters/opencode/mapper_emitters.go:24-28` (assistant text → `llm_response` PayloadRef, not an op at all).
**Proposed invariant**: `count(ops WHERE kind='llm') == count(ops WHERE kind='llm' AND EXISTS payload_ref kind='llm_response')` — drops the `assistant` clause entirely.
**Suggested fix**: Strike `kind='assistant'` from invariant #4 in the SOW; document that assistant output is modeled as the LLM op's response payload.

### ID: T8-canonical-1
**Invariant**: #8 / #9 (ERROR CAPTURE)
**Severity**: P1 (silent undercount risk on the most important invariant class)
**Description**: `SessionStatus` is a typed string enum with five documented constants (`events.go:49-66`). **Ops and turns have no equivalent.** `OpFinalizedEvent.Status` (`events.go:313`) and `TurnFinalizedEvent.Status` (`events.go:252`) are bare `string`. Invariant #8 filters `status='failed'`, but nothing in the canonical model guarantees adapters emit exactly `'failed'`. A scan of adapter source shows **four** status literals in play: `ok` (31 sites, the ai-agent source format), `completed` (13 sites, the canonical emit), `failed` (2), `cancelled` (1). If any adapter emits `'error'` or `'errored'` for a failure (a very common convention), invariant #8 silently reports zero failures and the gap is invisible.
**Evidence**:
- `internal/canonical/events.go:313` — `Status string` (free-text, no enum).
- `internal/canonical/events.go:252` — same for turns.
- `rg` over `internal/adapters/**/*.go` for `Status: "..."` yields `ok`×31, `completed`×13, `failed`×2, `cancelled`×1.
- Contrast: `SessionStatus` *is* an enum at `events.go:49-69`.
**Proposed invariant**: Add `type OpStatus string` with constants (`StatusOpCompleted`, `StatusOpFailed`, `StatusOpCancelled`, `StatusOpRunning`), mirror for turns, and add a per-adapter normalization table to the matrix spec. Then #8/#9 become `status = OpFailed`.
**Suggested fix**: Define the enum; **verify whether aiagent_v2's source `"ok"` is normalized to `"completed"` before the row is written** (I could not confirm the normalization path in `aiagent_v2/mapper.go` from this pass — flagging as an open question for reviewer #4). This is the single highest-risk silent gap in the invariant set.
**Open questions**: Does the aiagent_v2 mapper normalize `ok`→`completed`? If not, the live DB already has mixed status strings and the invariant baseline numbers in the SOW are unreliable.

### ID: T10-canonical-1
**Invariant**: #10 (EXTERNAL SUBAGENTS)
**Severity**: P2 (field exists and is correct; the gap is per-adapter capability, not schema)
**Description**: `ChildSessionNativeID` exists in the canonical model (`events.go:298`) and the schema (`schema_contract_test.go:388`, `ops.child_session_id TEXT` with FK to sessions). **Evidence**: `events.go:296-298` (field present, optional); `schema_contract_test.go:404` (FK present).
**Proposed invariant**: `count(kind='session' ops WITH child_session_id IS NOT NULL) / count(kind='session' ops) WHERE adapter_supports_deterministic_subagent_link(source_id) = 1`. The capability matrix is the gate.
**Suggested fix**: Accept the field as sufficient; drive the 0% number down via per-adapter remediation SOWs (chunk 4), not a schema change. Refutes any claim that #10 needs migration.

### ID: T11-canonical-1
**Invariant**: #11 (TURN VIEWER PRESENTS ALL CAPTURED INFO)
**Severity**: P2 (captured data is invisible to the operator)
**Description**: `ops.reasoning_kind` is a first-class canonical field (`events.go:295`, values `'summary'|'raw'`) and a persisted column (`schema_contract_test.go:370`), but **no frontend file references it** — neither snake_case `reasoning_kind` nor camelCase `reasoningKind` appears anywhere under `frontend/src/`. ## OVERALL ASSESSMENT

The canonical model is **well-designed for invariants #3, #5–#10**: every field those invariants need exists in both the Go types and the SQL schema, with correct indexes and FKs. The reviewer confirms the SOW's "schema sufficient" claim for that subset and refutes any suggestion that #6/#7/#10 need migration.

The canonical model is **incoherent for invariants #1, #2, #4**: those invariants query op kinds (`user_input`, `assistant`) that the `OpKind` enum does not define and no adapter emits. The SOW treats these as adapter-population gaps; they are in fact **canonical-contract gaps** that must be resolved (by enum extension or by invariant re-framing) before any invariant code is written. This is the single most important correction to the SOW.

A secondary structural gap is the **absence of a typed `OpStatus`/`TurnStatus` enum** (T8-canonical-1): sessions have one, ops and turns do not, and the codebase already shows four status literals in flight. This makes the error-capture invariants (#8/#9) fragile in a way the SOW does not acknowledge.

Finally, six canonical fields are captured-and-persisted-but-UI-invisible (T11-canonical-1..4), undermining invariant #11's "presents all captured information" promise.

## THINGS THE CTO MISSED

1. **The `user_input`/`assistant` op-kind absence is a canonical-contract defect, not an adapter gap.** The SOW's known-gaps baseline lists `count(ops WHERE kind='user_input')` as if it's a runnable query; it returns 0 for *every* adapter by construction, so it cannot detect the codex-vs-opencode inconsistency the CTO actually wants to catch.
2. **codex's "24,149 internal ops (likely user_input misclassified)" is a misread.** Those `internal` ops ARE the user inputs, emitted intentionally (`codex/ops_response.go:160`). The real issue is that the *canonical model* gave codex no first-class kind to use, so it overloaded `internal`. Flagging them as "misclassified" would lead a fixer to delete them, destroying the only user-prompt signal codex has.
3. **No typed `OpStatus` enum** — the `status='failed'` filter in #8/#9 is unguarded. The aiagent `"ok"` literal in particular needs verification that it's normalized before the DB write; if it isn't, the live-DB baseline numbers are already wrong.
4. **Six captured-but-unsurfaced fields** (reasoning_kind, bytes/chars in-out, turn cache tokens + error_class, provider_alias, call_path, sha256). Invariant #11 cannot pass today regardless of adapter behavior.
5. **The SOW's "Schema impact: none" line should be split** into "SQL schema: none" (true) and "Canonical contract: #2/#4 need a decision" (currently missing), so chunk-2 implementation doesn't stall on an undiscovered design question.
6. **For Part B**: gemini-cli's heavy use of reasoning ("thoughts") would immediately expose the `reasoning_kind` UI gap — adding it as adapter #6 before fixing T11-canonical-1 would ship a new data dimension the operator still can't see.
